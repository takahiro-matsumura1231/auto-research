# 研究の進め方

このテンプレートが前提にしている進め方を説明する。規則そのものは [AGENTS.md](../AGENTS.md) にあり、ここではその理由と、1つの実験が始まってから論文に載るまでの流れを書く。

## 全体像

```
フェーズ0  探索を凍結し、正式リポジトリを開く
   │
研究ラウンド（何度でも繰り返す）
   │  /new-round    問い・出発点・計画・台帳
   │
   │  ┌─ 実験1件ごとに ────────────────────────────────┐
   │  │ 1. 監査       保存済みの予測や失敗例を見て仮説を立てる  │
   │  │ 2. 登録       /preregister  採点前に条件を凍結           │
   │  │ 3. 確認       smoke test、checkpointの再読込、ハッシュ   │
   │  │ 4. 実行       途中の精度で止めない・選ばない              │
   │  │ 5. 報告       /report-result  登録どおりに集計して照合   │
   │  │ 6. 判断       /record-decision  採否・次の一手           │
   │  └──────────────────────────────────────────────┘
   │  /linear-sync で台帳・progress・Linear をそろえる
   │
論文化ラウンド  /paper-evidence  主張 ↔ 根拠 ↔ 生成コード
```

## フェーズ0: 探索を凍結する

探索の段階では、速く試すほうが大事なので、規則はゆるくてよい。ただし、探索の結果をそのまま論文の数値にしてはいけない。正式な段階に移るときは次の手順を踏む。

1. 探索用のリポジトリを**丸ごと**コミットし、タグを打つ（例: `exploratory-v1`）。整理や削除はしない。
2. 新しい正式リポジトリ（このテンプレート）を開き、探索から必要なものだけを選んで持ち込む。
3. 探索で出た主要な数値を1つずつ再計算し、「何の値だったか」を記録する（`docs/provenance/` を作るとよい）。
   - 実際に起きた例: 見出しの「MAE 1.97」が、5 fold中4 foldだけの平均だった。正しい値は2.05で、1.97は取り下げた。
4. 文書どうしの矛盾を一覧にし、後のどのフェーズで解消するかを決める。
5. 以上を判断ログの 0001 に書く。

## 研究ラウンド

ラウンドは「指導教員のフィードバックを受けてからの一区切り」「論文化」のような管理単位。`docs/rounds/<round>/` に置く。

- **README.md（台帳）**: 作業ID、順序、作業、状態、完了条件・証拠のリンク。状態は `候補 / 未着手 / 調査中 / 設計中 / 登録済 / 実行中 / 分析中 / 完了 / 保留 / 中止`。
- **plan.md**: 検討する順番と、各段階を終える条件。順番は**検討の順番**であって、全部やる約束ではない。根拠・費用・実行可能性を見て、不要なら理由を書いて `保留` にする。
- **progress.md（追記専用）**: 日付ごとに、背景・実施・結果・限界・証拠・判断・次の行動を書く。

最初の作業は、たいてい次の2つにする。

1. **基準点の固定**: 保存済みの予測を独立したスクリプトで再集計し、既報の値と一致することを確かめる。
2. **誤差・失敗例の監査**: どの事例を見るかの**抽出規則を、画像やデータを見る前に**書く。その後に見る。こうすると、都合のよい例だけを拾ったという疑いを避けられる。

この2つから仮説を立て、実験の優先順位を決める。

## 実験1件の流れ

### 1. 採点前登録（/preregister）

外側の評価データを採点する**前に**、次を凍結する。

- 問いと方向仮説（「Xを変えるとYが下がる」）
- 対照と候補。何を変え、何を変えないか
- 分割、seed、採点単位の数、予算（見込みのGPU時間）
- 主要量は**1つ**。区間の計算方法（例: クラスタ単位のbootstrap、反復回数、乱数seed）
- 副次量と、それらは探索的に報告すること
- 採用を検討する条件（例: 主要差が負で、95%区間の上端が0未満、推論時間の増加が20%以内）
- 失敗時の扱い（OOM、欠測）
- checkpointの保存先と、再読込の確認方法
- この比較の限界（例: 既に使った fold での遡及的な比較であり、新しいデータでの性能ではない）

文書（`docs/protocols/<id>_protocol.md`）、機械可読の設定（`configs/<id>.yaml`）、集計スクリプトを書き、SHA-256を記録する。判断ログに1件、Linear に Issue を1件作る。

**登録は、独立したレビュー（reviewer サブエージェント）を通してから確定する。** 実例では、レビューでseedを混ぜた平均の誤りが見つかり、登録前に直せた。

### 2. 実行前の確認

- 関連するテストが通る
- 小さい規模の smoke test が最後まで通る。**同じ予測を候補と対照の両方に入れて、差が0、区間も[0, 0]になる**ことを確かめる（集計スクリプトの検査）
- checkpointを保存し、再読込して同じ予測が出る（`tools/check_checkpoint.py`）
- 入力・コード・設定のハッシュを保存する（`tools/snapshot_sources.py`）

### 3. 実行

- 途中の精度を見て止めない、選ばない。
- バックグラウンドで実行し、PIDとログの場所を progress に書く。
- 再開するときは、既存の結果とcheckpointを消さない。

### 4. 報告（/report-result）

- 登録した集計スクリプトだけで主要量・副次量を出す。
- 数値は `tools/verify_doc_numbers.py` で照合する。
- 主要量の結果を、条件を満たしたかどうかとともに先に書く。満たさなかった結果も同じ詳しさで残す。
- 「何を示し、何を示さないか」を書く。
- 推定値、foldやseedのばらつき、区間を分ける。

### 5. 判断（/record-decision）

採否、標準モデルの変更、次の実験などを判断ログに書く。判断ログの各項目には「決めたこと」「理由」「無効にするもの」「約束すること」を書く。

## 中止と保留も記録する

実例: 高粒数帯の損失を重くする実験（E02）は、登録して実行を始めた後、研究上の優先度を見直して**外側foldを1つも採点しないうちに**中止した。中止の理由と状態をファイルに残し、台帳は `中止` にした。採点した後の中止は「結果を見て選んだ」ことになるので、採点前に止めたことを記録しておくのが大事。

## 同じデータでの繰り返し判断

前の実験の結果を見て次のarmを選ぶと、同じデータで判断を重ねることになる。それ自体は悪くないが、その場合は

- そのことを判断ログに書く
- 最終性能は、**全ての選択を終えた後に、一度も使っていないデータで一度だけ**評価する
- それまでの値は「遡及的な相対比較」と呼ぶ

## 論文化

論文化も1つのラウンドとして開く（`/new-round` で `paper` など）。新しい比較学習は既定の作業に含めない。

1. `docs/paper/paper_brief.md` で目的、投稿先、主張を固める。
2. `docs/paper/evidence_index.md` で、主張ごとに根拠（プロトコル、結果、集計値、生成コード、manifest）を結ぶ。
3. 図表は `tools/` のスクリプトから生成し、手で数値を入れない。
4. 保存済みの予測・checkpoint・manifest・プロトコルにたどれない値は、論文の確定値にしない。
5. 内部ラベル（実験ID、Issue番号）は本文に出さない。

## エージェントとの分担

- 読み取りや数値の抜き出しは安いモデル（reader）に任せ、判断に使う数値は親エージェントが元データで計算し直す。安いモデルは数値をときどき間違える（実例: 47を48と報告した）。
- 実装は worker に任せられるが、プロトコルとの一致は reviewer が独立に確かめる。
- 最終判断と、ユーザーへの報告は親エージェントが行う。
